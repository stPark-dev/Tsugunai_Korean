## PoC3 — 대사 줄 폭 상한 (2026-11-12, 통과)

- 빌드: `python -m tools.build_poc3 orig/tsugunai.bin build/poc3.bin` (M00_25 대사 줄을 전각 25/26/27자, 반각 문자 줄로 교체)
- 관찰(`work/shots/p3*.png`):
  - 엔진이 화자 대사의 첫 줄 앞에 `『`, 마지막 줄 끝에 `』`를 붙이고, 둘째 줄부터 1칸 들여 씀.
  - op 0x37 x = 창 왼쪽 희망 위치. 오른쪽이 화면 끝(약 608px)을 넘으면 창을 왼쪽으로 밀고, 그래도 넘치면 왼쪽이 화면 밖으로 잘림.
  - `『` + 25자 + `』` = 27칸 → 다 보임. `『` + 27자 = 28칸 → 첫 글자 잘림. **상한 27칸.**
  - 반각 영숫자(0x21–0x7E)는 화면에 그려지지 않지만 창 폭 계산에는 들어감 → 번역문 사용 금지.
  - 반각 공백 1개 = 약 전각 1칸(정밀 측정 아님).
- 결론(빌드 검사 규칙 후보): 대사 한 줄 ≤ 25칸(괄호·들여쓰기 2칸 여유). 번역 목표는 22칸 이하.
- 미해결: 화자 없는 서술(괄호 없음)의 여유, 한 페이지 최대 줄 수(원문 최대 3줄 관찰), 공백 폭(한국어 띄어쓰기 비용 — 좁은 공백이 필요하면 코드 수정 필요).

## PoC4 — 데이터 파일 재배치·실행 파일 문자열 수정 (2026-11-13, 부분 통과)

- 빌드: `python -m tools.build_poc4 orig/tsugunai.bin build/poc4.bin` (폰트 원본, 일본어 표지)
  - 데이터 파일: 아이템·소지품·마법·퀘스트 기록 전부 앞에 `＊` → ITEM 14,992→15,584 B 등 레코드 재배치.
    무기 필살기·호부 소환수 앞에 `デ`, 몬스터 앞에 `敵`.
  - 실행 파일(크기 동일): 제자리 수정(`オプション４`, 메모리카드 메시지 3줄), 재배치(`PUSH ANY BUTTON` 줄 → 디버그 문자열 자리 0x255800, 참조 7곳 수정 / `たたかう` → 0x254c08),
    필살기·소환수 표에 `実`·`実１`·`実２`, 기본 이름 후보 3곳에 `レイア`·`レイカ`·`レイタ`.
- 관찰(`work/shots/poc4/`):
  - 옵션 제목 `オプション４` 표시. 옵션 줄(`メッセージスピード　　　遅い　…`)은 전각 공백으로 열을 맞춤 → 번역도 열 위치 유지 필요.
  - 메모리카드: 제자리 2줄과 옮긴 `PUSH ANY BUTTON ＰＯＣ４移…` 정상 표시. 이 창은 한 줄 약 22칸, 넘치면 창 밖으로 나감.
  - 메뉴 상태·아이템·장비 화면: 아이템·무기·방어구 이름과 설명이 전부 `＊` → **커진 ITEM.DAT 정상 로드**, 무기 이름·설명은 ITEM.DAT 에서 옴(WEAPON.DAT 이름·설명은 이 화면에서 안 씀).
  - 퀘스트 화면: 제목·설명 `＊` → **커진 RECORD.DAT 정상 로드**. 설명은 약 13칸에서 자동 줄바꿈. `説明：`·`（実行中）`는 실행 파일 문자열.
  - 이름 입력: 가나 표가 세로 열로 배치(실행 파일의 5글자 묶음 = 화면의 한 열). `デフォルト` → `レイタ` → **기본 이름은 `.sdata` 이름 표 0x25d008**(ミミー·ナビ·レイス·ギルス·アモル·漁師·ビルド 7칸, 대사 `{n:01}`~`{n:07}` 후보). `.data` 의 `レイス` 2곳은 이 화면에서 안 씀.
  - 상태 메뉴 항목(アイテム·魔法·装備…)은 실행 파일 문자열이 아님 → 그림 글자 G4.
- 미확인(전투가 필요): 옮긴 `たたかう`, 필살기·소환수 이름 출처(데이터 파일 vs 실행 파일 두 표), 몬스터 이름(EST), 마법 설명, 소지품 화면.
- 결론: 데이터 파일 재배치와 실행 파일 문자열 제자리·재배치 방식 채택. 남은 항목은 전투 진입 후 확인.

## PoC5: 이름 뒤 조사 훅 (D8) — 통과

- 질문: 실행 중 실제 이름의 마지막 글자 받침을 보고 `{j:A/B}` 의 A·B 를 고를 수 있는가?
- 정적 분석(2026-11-16, 원본 SCPS_110.07):
  - 대사 펼치기 함수 0x1b3a98(호출 22곳, 화자·대사·선택지 공용): 문자열 → 8바이트 글리프 항목(u16 코드, x, y, 색).
    전각 x+22, 반각 ASCII x+14. `01 xx` 색, `02 xx` 이름 = 저장 데이터(gp-0x4928) + 0x66 + xx×22 복사.
    그 밖의 0x20 미만 바이트는 1바이트 건너뜀(0x1b3b48) → 새 제어 코드를 넣을 자리.
  - 이름 버퍼를 읽는 다른 곳(0x10c094, 0x131020, 0x19398c, 0x1a848c, 0x1a98d0)은 메뉴·상태용 이름 복사 → 조사와 무관.
  - 글자 그리기 경로: 0x1a13f8(한 글자, 0x20·0x8140 건너뜀) → 글리프 캐시 0x1a1068/0x1a11a0 → 0x1a0f28 → 코드표 이분 탐색 0x1a0c10.
- 설계:
  - `{j:A/B}` → `03 xx`(xx = 조사 쌍 표 번호). 훅은 바로 앞 글리프 항목의 코드(= 이름 마지막 글자)를 보고 A·B 문자열을 같은 방식으로 펼친다.
  - 받침 판정을 비교 한 번으로: 빌드가 한글 음절을 한자 슬롯 코드에 배정할 때 받침 있는 음절을 앞(LO ≤ 코드 < SPLIT), 없는 음절을 뒤에 둔다. 한글이 아닌 끝 글자는 받침 없음으로 본다.
  - 훅 코드·조사 표 자리: 0x1bf380–0x1bf77c(1KB) 함수. 디버그 좌표 출력(`id %5d x%5d y%5d`)이고 jal·j·분기·포인터·lui/addiu 참조가 하나도 없음. 그 함수의 점프 표 0x255720 도 같이 안 쓰임.
- 정적 검증: `tests/test_josa_hook.py` — 원본 실행 파일의 펼치기 함수에 훅을 붙여 작은 MIPS 해석기(`tests/mips_sim.py`)로 실행.
  받침 있음/없음, 3자 조사, 다른 이름 변수, 모르는 제어 바이트 건너뛰기 확인. 훅을 일부러 망가뜨리면 실패함(변이 확인).
- 이름 확정 경로: 0x18e1e0 이 이름 끝의 채움 `　`(0x8140)을 지운 뒤 저장 → 저장된 이름의 마지막 글자가 실제 끝 글자.
- 빌드: `python -m tools.build_poc5 orig/tsugunai.bin build/poc5.bin [주인공 기본 이름]`
  MQ00 번역 전체 + 한글 399음절(한자 슬롯, 받침 범위 0x889f–0x8bb9) + 조사 쌍 12개 + 훅. 파일 재배치 없음.
- 관찰(PCSX2, `work/shots/poc5/`):
  - MQ00 대사·화자 이름이 한글로 표시(첫 장면, 배 위 병사 대화).
  - 이름 입력 デフォルト → 기본 이름 「레온」 표시 → M00_21#026 **「레온이었던가．」**(14_crop.png), 화자 이름도 「레온」.
  - 기본 이름 「레이스」 이미지(poc5b) → **「레이스였던가．」**(b_14_crop.png).
  - 실행 파일 문자열의 한자는 슬롯이 한글로 바뀌어 깨짐(決定 → 「旦定」 비슷) — 실행 파일 번역 전이라 예상된 결과.
  - 22px 화면에서 「이」의 좁은 ㅇ 이 「에」처럼 보이기도 함 → 글꼴·크기 선택 때 가독성 확인 필요.
- 코드 리뷰 후 수정: 조사 쌍 번호를 1부터(0번 칸은 빈 칸) — 0 이면 `03 00` 의 NUL 에서 문자열이 끊김(첫 쌍 과/와, MQ00 엔 없어서 PCSX2 확인 땐 안 드러남).
  반각 가나·제어 문자 거부(펼치기 함수가 0x80 이상을 2바이트로 읽음). 바뀐 표 배치는 해석기 테스트로 확인, PCSX2 재확인은 안 함.
- 이름 입력(D9, 같은 PoC5 이미지): 히라가나·가타카나 쪽을 `text/name_grid.txt` 180음절로(`tools/name_grid.py`, 열 문자열 제자리 교체),
  화면 글자(이름 입력·한글１·한글２·영문・숫자·기본 이름·결정·뒤로·앞으로)는 실행 파일 문자열 제자리 번역.
  - 열 문자열 하나 = 화면의 한 **행**(5칸). 쪽마다 왼쪽 묶음 10행 + 오른쪽 묶음 8행. 처음 이름 칸에는 기본 이름이 들어 있고 고른 글자가 커서 자리를 덮어씀.
  - 1쪽에서 「민」, 한글２ 로 바꿔 「준」 입력 → 결정 → **「민준이었던가．」**(n_08c.png). 입력 → 저장 → 대사 → 조사 훅이 한 줄로 이어짐.
  - 가독성 문제 확인: 「이」→「에」, 「기」→「게」처럼 보임. 팔레트는 16칸 모두 흰색(알파만 다름)이고 원래 글리프 획은 약 3px.
    Noto Sans 20px 의 얇은 획(약 2px)·좁고 높은 ㅇ 이 원인으로 보임 → 이 크기에 맞는 굵은 글꼴 선택·렌더링 조정 필요(라이선스 확인 포함).
- 결론: 조사 훅 방식 채택. 남은 일: 한글 이름 입력(가나 표 대체), 빈 이름일 때 동작, 빌드 정식화(글리프 배정이 넘치거나 빠진 글자면 실패).
